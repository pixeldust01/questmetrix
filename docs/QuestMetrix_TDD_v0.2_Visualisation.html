📚 Understanding the Telemetry Pipeline

A guided tour through the cause-and-effect flow of data in QuestMetrix.

1. The Event Contract

Every event flowing through QuestMetrix must match a strict schema. This is the contract between your game and the analytics platform.

{
  "event": "enemy_killed",      // string - type of event
  "player_id": "player_001",    // string - who did it?
  "game_id": "demo_game",      // string - which game?
  "timestamp": "2026-08-11T00:00:00Z", // string - when?
  "level": 1                    // integer - where?
}
Field Type Required Description
eventstringYesIdentifier for the event type
player_idstringYesUnique player identifier
game_idstringYesGame/project identifier
timestampstringYesISO 8601 format date-time
levelintegerYesGame level for the event

2. Event Registry

QuestMetrix defines supported event types. Each type captures a specific player action with a purpose.

Event Status Purpose
enemy_killedImplemented ✓Records enemy defeat
level_startedPlannedRecords level start
level_completedPlannedRecords level completion
player_diedPlannedRecords player death
item_collectedPlannedRecords item collection
player_quitPlannedRecords player leaving

3. The Validation Journey

✅ Valid Event
HTTP 200 OK → Event stored to PostgreSQL
Example: {"event": "enemy_killed", "player_id": "player_001", "game_id": "demo_game", "timestamp": "2026-08-11", "level": 1}
❌ Invalid Event
HTTP 422 Unprocessable Entity → Event rejected
Example: Missing "level" field → Pydantic validation error

5. What Happens When Things Go Wrong?

Escalating Errors
Attempt 1 → fails → wait
Attempt 2 → fails → wait longer
Attempt 3 → fails → Dead Letter Queue
Retry with bounded backoff, never unlimited retries!
HTTP Status Code Playbook
400: Malformed request
422: Schema validation failure
429: Rate limit exceeded
500: Unexpected server error
